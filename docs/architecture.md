# Architecture

For developers. Explains how the code is organised and the reasoning behind the main decisions.

> This project runs **Next.js 16**, which differs from older versions. Notably: `middleware.ts` is now **`proxy.ts`**; `params` and `searchParams` are **Promises** you must `await`; and route prop types (`PageProps<"/path">`, `LayoutProps<"/">`) are global helpers generated by `next typegen`. The framework guides are in `node_modules/next/dist/docs/`. `AGENTS.md` (managed by `next dev`) points AI assistants there.

## Overview

```
Browser ──> Next.js app ──> Supabase
              │              ├─ Postgres (tables, views, functions, RLS)
              │              ├─ Auth (staff email + password)
              │              └─ Storage (coach + participant photos)
              │
   public pages ── anon key ── two read-only views
   /admin       ── staff session ── tables (limited by RLS)
   /m, /checkin ── anon key ── check-in functions guarded by a secret token
   /member      ── member session ── my_* functions (own data only)
   secret key (server only) ── create logins, reset passwords, member photos
```

There is **no custom API server**. Pages are Server Components that query Supabase directly, and changes go through Server Actions. Security lives in the database (RLS), so the same rules will automatically cover the future mobile app.

## Supabase clients

Five small factories, each for one situation:

| File | Used in | Notes |
|---|---|---|
| `lib/supabase/server.ts` | Server Components, Server Actions | Reads/writes the auth cookies. Acts **as the signed-in user**, so RLS applies to them. |
| `lib/supabase/client.ts` | Client Components | Browser client. Currently unused by the UI, ready for the app/PWA. |
| `lib/supabase/proxy.ts` | `proxy.ts` | Refreshes the session cookie on each `/admin` request. |
| `lib/supabase/public.ts` | Public pages, QR check-in | No cookies, anon key. Caches results for 5 minutes; `{ fresh: true }` disables caching (used for QR calls). |
| `lib/supabase/admin.ts` | Server Actions only | **Secret key**, bypasses RLS, `server-only`. See below. |

## Authentication and authorization

Staff sign in with email and password (`app/admin/login/actions.ts`). Access is checked in **four layers**, each independent:

1. **`proxy.ts`** — redirects visitors with no session away from `/admin/*`. This is only a fast, optimistic check.
2. **`requireStaff()` / `requireAdmin()`** (`lib/auth.ts`) — called in the admin layout **and in every page and Server Action**. It re-verifies the session with Supabase (`getUser()`) and loads the `staff_profiles` role. Pages call it themselves because layouts do not re-run on client-side navigation.
3. **Server Actions** re-validate all input and re-check the role, because actions can be invoked by direct POST, not only from the UI.
4. **RLS** in Postgres enforces the final rules regardless of what the app does. See [database.md](database.md#access-rules-row-level-security).

Signing in is not enough — an account must also have a `staff_profiles` row. Coaches vs admins: admin-only pages call `requireAdmin()` and the nav hides them from coaches, but RLS is what actually blocks the writes.

## Data flow patterns

**Reading:** Server Components `await createClient()` then query. Lists cap their result size (participants 200, check-in 1000).

**Writing:** forms post to Server Actions (`actions.ts` next to each feature). Client form components use `useActionState` to show errors; on success actions call `revalidatePath(...)` and usually `redirect(...)`.

**Check-in screen** (`components/admin/check-in-list.tsx`): a Client Component that updates the UI immediately when a name is tapped, calls the `setAttendance` action, and rolls the change back with a message if the save fails.

**Photos:** uploaded in the same Server Action that saves the record (this is why `serverActions.bodySizeLimit` is raised to 6 MB in `next.config.ts`). Coach photos store a public URL; participant photos store a private storage path that is converted to a 1-hour signed URL when displayed, using a plain `<img>` so the image optimizer never caches private photos.

## Caching and freshness

- Public pages (`/schedule`, `/coaches`) read through `lib/supabase/public.ts`, whose `fetch` is cached for 300 seconds, so they are served statically and stay fast.
- When an admin saves a class or coach, the action calls `revalidatePath('/schedule')` / `('/coaches')` so the public site updates **immediately**.
- All `/admin` pages and `/m/[token]` are dynamic (never cached).

## Time and dates

The gym is in the Philippines. "Today" and "day of week" are always computed in **`Asia/Manila`**, not the server's or browser's timezone: `gymToday()` in `lib/constants.ts` for the app and `gym_now()` in SQL for the QR functions. Dates like `session_date` are plain `YYYY-MM-DD` strings and are formatted without timezone conversion (`formatDate`) to avoid off-by-one-day bugs. `day_of_week` uses 0 = Sunday; the public schedule displays Monday first.

## Member area: My Progress, Settings and QR check-in

Two separate ways in, with different strength:

**1. Logged-in member area (`/member/*`) — progress and settings.** Members sign in with a username + password (Supabase Auth; internal email `<username>@members.sbg.local`). Everything reads from three SQL functions — `my_profile`, `my_progress`, `update_my_profile` — that identify the caller by `auth.uid()` and return only their own data, so coach-only notes can never leak (tested in `npm run db:test`).

- `app/member/login` — sign-in. `app/member/change-password` — required after a reset.
- `app/member/(secure)` — the protected area: `layout.tsx` calls `requireMember()` (`lib/member-auth.ts`), applies the member's chosen theme via `<ThemeScope>`, and shows the header/tabs; `page.tsx` is My Progress; `settings/` is the profile form.
- `proxy.ts` redirects signed-out visitors from `/member/*` to `/member/login` (optimistic check); `requireMember()` re-verifies on every page and action.
- Members can't write to storage, so their own photo goes through a Server Action that verifies them, then stores it with the server-side secret client.

**2. Personal QR link (`/m/<token>`, `/checkin`) — check-in only.** Each participant has a secret `checkin_token`; their QR encodes `<SITE_URL>/m/<token>`. It shows their name and today's classes with a **Check in** button (via the anon-callable `member_checkin_info` / `member_check_in` functions). Opening it saves the token in that phone's `localStorage` so the poster QR at the door (`/checkin`) can forward them to it. It no longer exposes progress. Pages are `noindex` with `Referrer-Policy: no-referrer`.

Staff and member accounts share Supabase Auth but are separate by role: `requireStaff()` needs a `staff_profiles` row, `requireMember()` needs an active participant linked by `user_id`.

## Accounts, password resets and the secret key

Some actions must do what a normal signed-in user may not: create a login for someone else, set another person's password, store a member's own photo. They use `lib/supabase/admin.ts` (the Supabase **secret key**, from the non-public `SUPABASE_SECRET_KEY`):

- The file starts with `import "server-only"`, so the build fails if it is ever imported into browser code.
- It is used **only inside Server Actions, after** `requireStaff()` / `requireAdmin()` / `requireMember()` has verified the caller.
- `lib/account-tools.ts` builds the text, sends it (`lib/sms.ts` — Semaphore, Twilio, or a manual `sms:` fallback), and writes the who/when to `sms_log` (never the password). `lib/phone.ts` normalises numbers; `lib/passwords.ts` makes random temporary passwords.
- Forced password change: `must_change_password` (on `staff_profiles` / `member_settings`) makes `requireStaff()` / `requireMember()` redirect to the change-password page until they choose their own.

See [accounts-and-sms.md](accounts-and-sms.md).

## Size limits

`lib/storage.ts` compresses every photo with `sharp` (≤1024 px WebP) and `lib/limits.ts` checks the project's size budget (`usage_bytes()`) before accepting an upload. Admin → Usage shows the numbers. See [data-limits.md](data-limits.md).

## Styling and loading screens

Tailwind CSS v4. Colours are CSS variables at the top of `app/globals.css`, exposed as Tailwind colours (`bg-brand`, `text-muted`, `border-border`…), with light and dark variants that follow the visitor's system setting. The palette is the logo's: **white, black, red (`--brand`) and blue (`--accent-text`)**, with a red→blue gradient on big headings.

- **Seamless background:** one fixed layer (soft blue/red glows + a faint grid) sits behind the whole site and page sections are transparent, so there are no coloured bands.
- **Glass cards:** `.card` is a translucent, blurred surface with a soft shadow. Other reusable classes are defined with `@utility` in the same file: `btn-primary`, `btn-secondary`, `btn-danger`, `field`, `label`, `text-gradient`, `eyebrow`, `skeleton`.
- **Member themes:** `<ThemeScope>` (`components/member/theme-scope.tsx`) sets `data-theme` (`light`/`dark`) and `data-accent` (`red`/`blue`/`mono`) on a wrapper; the CSS overrides the variables for everything inside, including its own copy of the background. Members choose these in Settings.
- **Motion:** `animate-fade-up`, `animate-float`, shimmer and belt-slide keyframes live in the `@theme` block; a `prefers-reduced-motion` rule switches animations off for people who ask for that.
- **Loading screens:** Next.js shows a route's `loading.tsx` while its page loads. `app/(public)/loading.tsx`, `app/m/[token]/loading.tsx` and `app/member/(secure)/loading.tsx` show the branded loader (spinning ring around "289" and a black belt with a sliding red tab); `app/admin/(protected)/loading.tsx` shows a shimmering ghost of a typical admin page. Buttons show "Saving…" states while an action runs.

To re-brand, change the variables at the top of `globals.css`.

## Accessibility conventions

Interactive targets are at least 44px tall (`min-h-11`); form fields have visible labels; errors use `role="alert"` and confirmations `role="status"`; the check-in rows are toggle buttons with `aria-pressed`; the heatmap has a text summary and the recent-sessions table as an accessible equivalent; the mobile menu works without JavaScript.

## Testing status

The database has an automated suite (`npm run db:test`, in-memory Postgres): triggers, member privacy, isolation, anon lock-out, size functions and indexes. The app code has no automated tests yet and is checked with `npx tsc --noEmit`, `npm run lint` and `npm run build`. Before relying on a change to access rules or check-in, test it manually with both an admin and a coach account (see the go-live checklist in [deployment.md](deployment.md#go-live-checklist)).
